How a request moves through three planes

Management accepts tenants, control owns their configuration, and data serves them. Nothing is pushed downstream: each child plane pulls from its parent’s database. Scroll the right-hand column and the map follows, or play any step on its own.

Read the map top to bottom

Each plane runs in its own Kubernetes cluster. On Azure, bootstrap prepares three: management, shared control and shared data. An operator can add a named isolated control/data pair later with a separate bootstrap command; tenant requests never create infrastructure.On Docker Desktop, only management exists at first. The provisioner creates the shared pair for the first shared tenant and an isolated pair for the first isolated tenant, reaching five kind clusters.

Inside each cluster the columns mean the same thing:

Left: entryAn API that checks the plane’s own X-Demo-Key.
Middle: statePostgreSQL in management and control; a ConfigMap and Redis in data.
Right: automationSetup Jobs with RadiusThe provisioner with Radius in management; a reconciler that polls every 5 s in control and data.

Dotted links always start at the child. A control reconciler reads management PostgreSQL and writes its report back; a data reconciler does the same against its control PostgreSQL. No API call travels from one plane to the next.

Onboard a tenant

One POST to management starts a chain of pulls. Management calls a tenant ready once control has created its record. It does not wait for data.

Admission assigns an available prepared pair inside management.accept_tenant, so provisioning_status is succeeded straight away. With no unused pair of the requested kind, admission returns 503 allocation_unavailable and creates nothing.

The provisioner takes one operation at a time. A second request while it works gets 503 provisioner_busy. The first shared tenant waits while management Radius creates the shared kind clusters.

Change configuration

After onboarding, control owns the message. A PUT to control creates the next desired version. The data reconciler picks it up on its next poll, rewrites the ConfigMap and reports config_applied.

Management supplied only the initial message. Later control polls call control.ensure_tenant again without replacing control’s newer versions.

Serve a data request

The data API answers from what is already in its cluster: the tenant’s ConfigMap and a Redis counter. It holds no parent database credentials, which is why it keeps serving when control or management is unreachable.

The counter key includes the onboarding_id, so configuration updates keep the count. Its service account data-api-runtime can get ConfigMaps and nothing in Secrets.

Each status reports one thing

Most confusion in a run comes from reading a status as broader than it is.

Where you read itWhat it means, and only that

A

Provision the first shared tenant

Proves one request reaches a working data response.

Accept shared-a management

make api ARGS='management GET /tenants/shared-a'   # 404 first
curl -i -sS --fail-with-body "$MANAGEMENT_URL/tenants" \
  -H "X-Demo-Key: $MANAGEMENT_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"tenant_id":"shared-a","isolation":"shared","initial_message":"alpha"}'
make api ARGS='management GET /tenants/shared-a'   # 404 first
printf '%s\n' '{"tenant_id":"shared-a","isolation":"shared","initial_message":"alpha"}' | \
  make api ARGS='management POST /tenants' > "$NOTES/shared-a-request.json"

Set MANAGEMENT_URL and MANAGEMENT_KEY as the guide shows, without printing the Secret. The operation is already succeeded with stage available.Watch the provisioner log while management Radius creates the shared clusters and installs child Radius.

Follow it to data control · data

make api ARGS='management GET /tenants/shared-a' | jq '{pair_id, provisioning_status, provisioning_stage, onboarding_status, control_record}'
make api ARGS='control:shared GET /tenants/shared-a'
make api ARGS='data:shared GET /tenants/shared-a'
make kube ARGS='shared-data get configmap tenant-shared-a -o json' | jq .data
  • provisioning_status: succeeded and onboarding_status: ready.
  • Control reports applied; data returns alpha, version 1, counter 0.
  • The same onboarding_id from all three APIs.

Stop on failed or interrupted. Never reset database status values to force a retry. Record pair_id and the two kube-system namespace UIDs for scenario B.

Increment one tenant data

F

Block the management database link

Proves a control/data pair keeps working while management PostgreSQL is unreachable.

Cut control’s link to management second terminal

make fault CONFIRM_AZURE=yes \
  ARGS='--slot shared-control --component control-reconciler --duration 300'
make fault CONFIRM_LOCAL=yes \
  ARGS='--slot shared-control --component control-reconciler --duration 300'

The helper applies a Cilium policy to the private database connection.kind’s default CNI does not enforce NetworkPolicy, so the helper blocks inside the reconciler Pod’s network namespace. It does not stop any API. In the main terminal, wait for blocked_verified, then keep working for at least 60 s:

FAULT_SLOT=shared-control
FAULT_COMPONENT=control-reconciler
make fault-status ARGS="'$FAULT_SLOT' '$FAULT_COMPONENT'" | jq '{slot, component, outcome, blocked_at, restored}'
printf '%s\n' '{"message":"without-management"}' | \
  make api ARGS='control:shared PUT /tenants/shared-a/configuration'
make api ARGS='data:shared GET /tenants/shared-a'
make api ARGS='data:shared POST /tenants/shared-a/counter'
  • without-management reaches data through control’s own database; the counter still increments.
  • Management’s response for shared-a does not change during the block.

After the timer restores it journal

make fault-status ARGS="'$FAULT_SLOT' '$FAULT_COMPONENT'" | jq '{outcome, restored, physical_restored, restoration_started_at, restored_at}'
  • verified_and_restored, both restoration flags true, and a successful control poll after restoration.
  • No duplicate control_record_created event.
G

Block control, queue updates, restart data

Proves data serves its applied configuration through an outage and a restart, then jumps to the newest version.

Cut data’s link to control, queue two versions second terminal

make fault CONFIRM_AZURE=yes \
  ARGS='--slot shared-data --component data-reconciler --duration 300'
make fault CONFIRM_LOCAL=yes \
  ARGS='--slot shared-data --component data-reconciler --duration 300'
FAULT_SLOT=shared-data
FAULT_COMPONENT=data-reconciler
printf '%s\n' '{"message":"queued-first"}' | \
  make api ARGS='control:shared PUT /tenants/shared-a/configuration'
printf '%s\n' '{"message":"queued-latest"}' | \
  make api ARGS='control:shared PUT /tenants/shared-a/configuration'
make api ARGS='data:shared GET /tenants/shared-a'
make api ARGS='data:shared POST /tenants/shared-a/counter'
  • Start only after F is restored, and wait for blocked_verified.
  • Control shows the latest version pending. Data keeps the pre-outage message and version; its counter still works.

Replace the data API mid-outage new Pod UID

make kube ARGS='shared-data rollout restart deployment/data-api'
make kube ARGS='shared-data rollout status deployment/data-api --timeout=30s'
make api ARGS='data:shared GET /tenants/shared-a'
  • A new Pod UID still returns the old applied message and version with the current counter.
  • Do not replace the data reconciler during the fault; the helper checks its Pod identity.

Reconnect and catch up journal

make fault-status ARGS="'$FAULT_SLOT' '$FAULT_COMPONENT'" | jq '{outcome, restored, physical_restored}'
make api ARGS='control:shared GET /tenants/shared-a'
make kube ARGS='shared-data get configmap tenant-shared-a -o json' | jq .data
  • Data shows queued-latest; control reports applied.
  • Both versions have configuration_updated events; queued-first never gets config_applied.

If a fault process stops without confirmed restoration, restore that exact fault with --restore as the guide’s Interrupted fault step shows. Never kill -9, replace the faulted reconciler or delete its cluster.

Proves keys are per plane instance, not per tenant.

One key, two tenants data · control

DATA_URL=$(make endpoints ARGS=shared-data | jq -er '.url') || exit 1

  • The shared control and data keys each return 200 for both shared-a and shared-b; the POST increments shared-b.

I

Observe a noisy neighbor

Records what one busy tenant does to another on the same pair.

Load shared-b, watch shared-a 4 workers · 60 s

for worker in 1 2 3 4; do
  (end=$((SECONDS + 60))
   while (( SECONDS < end )); do
     curl -q -sS -o /dev/null -w '%{http_code}\n' -X POST \
       -H "X-Demo-Key: $DATA_KEY" "$DATA_URL/tenants/shared-b/counter"
   done > "$NOISE/worker-$worker.txt") &
done
  • Zero shared-a errors, and a PUT made under load applied within a few polls.
  • shared-a’s counter is unchanged; shared-b’s rose by exactly the number of 200 responses.

This records latency and errors rather than asserting a threshold. There are no rate limits or per-tenant quotas, and every request is billable gateway traffic. The guide has the baseline probe and the timed PUT.

L

Block a ConfigMap update

Proves data keeps its applied configuration when it can’t write a new one, and control reports the failure.

Make one ConfigMap immutable, then PUT shared-data

make kube ARGS="shared-data patch configmap tenant-shared-a --type=merge '--patch={\"immutable\":true}'"
printf '%s\n' '{"message":"blocked-write"}' | \
  make api ARGS='control:shared PUT /tenants/shared-a/configuration'
make api ARGS='control:shared GET /tenants/shared-a' | jq '.data_config'
  • Control shows failed with config_apply_failed and config_write_failed.
  • Data keeps the previous message and version; its counter still works. shared-b stays applied.

Delete only that ConfigMap restore

make kube ARGS='shared-data delete configmap tenant-shared-a'
make api ARGS='control:shared GET /tenants/shared-a' | jq '.data_config'
  • After at most one poll with 404, data serves blocked-write, control reports applied, and the counter is unchanged.

An immutable ConfigMap can’t be made mutable again, so deletion is the only restore. Target only tenant-shared-a.
